## 零、一句话

**把「工作层」（原脏层）从缓存提升为节点间同步的主体；commit 从同步前提降级为历史书签。**

---

## 一、为什么要动：先看量出来的数字

所有数字都在本机（macOS / APFS）实测，脚本见提交记录。

| 测量项 | 结果 | 含义 |
|---|---|---|
| 写入（入队） | **0.02 ms/批** | 快得没话说 |
| 单次 `fsync` | **6.12 ms** | 比不 fsync 慢 10 倍（0.65 ms） |
| 提交 1 条 | **44 ms** | ≈ 1 次 blob fsync + 5 个 tree/commit 对象 fsync + ref |
| 提交 100 条 | **670 ms** | ≈ 100 × 6 ms（每条写入一次 blob fsync，在 commit 时集中兑现） |
| 提交耗时 vs 目录规模 | 100 文件 38.85 ms / 3000 文件 42.04 ms | **与目录大小无关**，是固定开销，不是树遍历 |
| 真实仓库提交密度 | `zero@main.chat` 1506 个 commit，单日峰值 **612** | 已是「一天几百次」量级 |
| 8000 次提交的仓库 | 34.2 MB，`rev-list` 305 ms | 提交数增长带来的链式遍历成本 |

### 结论

1. **「commit 太频繁」的真实代价不在 commit 本身，而在「每条写入一次 fsync」。**
   一天写 3000 条 = 18 秒纯等磁盘。这与 commit 次数几乎无关。
2. **commit 的固定开销 44 ms/次** 主要也是 fsync（5~6 次）。
3. **真正要治的是「同步依赖 commit」这个结构性约束**——它使得「跨机可见性」与「历史整洁」被迫对立：
   - 频繁 commit → 历史碎成几百条/天，链式遍历成本上升
   - 不频繁 commit → 另一台机器几小时看不到新记忆

## 二、核心决策：工作层是主体

### 现在的模型

```
干净层（objects/ + refs/）  ← 真相，跨机同步只搬这一层
脏层（dirty/<branch>/*.dirty）← 缓存，进程内临时状态，不同步
commit = 把脏层折叠成干净层 = 同步的前提
```

### 目标模型

```
工作层（原脏层）             ← 主体。写入直接落这里，节点间直接同步这一层
提交层（HEAD 以下的历史）     ← 快照。commit = 「此刻在此处拍了一张照」
```

**这其实就是 Git 自己的工作树模型**：工作树是主体，commit 是快照。
现有脏层的物理格式（`S`/`D`/`B` 三行前缀的纯文本命令流）本来就是工作树的表示，
所以这不是重写，是**改变它的地位**。

### 明确不做

- **不重写现有存储层**。`dirty.go` / `gitstore` 的编解码、折叠、单写者队列全部保留。
- **不废弃 Git**。commit 层仍然是 Git，外部工具照样 `clone` / `fetch`。
- **不引入第二套网络协议给 Agent**。Agent 侧仍然只走 MCP。

## 三、四条正交轴

系统现在的可配置维度彼此独立，可任意组合。

| 轴 | 选项 | 是否正交 |
|---|---|---|
| **1. 存储位置** | 本地全量（Center） / 本地增量 + 按需缓存（Edge） | 是 |
| **2. 嵌入模型** | 远端大模型 / 本地小模型（ONNX int8） / 纯 BM25 | 是 |
| **3. 向量索引目录** | `<vectors>/<model>/`，多份共存 | 是 |
| **4. 固化策略** | 工作层命令流（秒级） / Git commit（按需或每日） | 是 |

### 为什么它们正交

- 存储：`path → bytes`，是纯函数
- 嵌入：`text → vector`，是纯函数
- 两者互不知道对方存在，所以可以任意搭配

### 组合示例（都是合法部署）

| 存储 | 嵌入 | 形态 | 占用 |
|---|---|---|---|
| 本地全量 | 远端 bge-m3 | 中心节点（现行 3060） | 全量数据 + 远端推理 |
| 本地全量 | 本地 ONNX | 单机自洽、零网络零显存 | 数据 + 23 MB 模型 |
| 本地增量 + 中心 | 本地 ONNX | 边缘分身，断网可降级 | 少量数据 + 55 MB |
| 本地增量 + 中心 | 纯 BM25 | 极轻分身（树莓派 / 小 VPS） | 0 MB 模型 |

## 四、同步协议：先 tree，后 blob

### 决策

```
① 拉对方的 tree / 命令流
② 本地应用：增（S）、删（D）、抹除（X）、替换（R）
③ 全部应用完之后，才去拉「最终结果里仍然存在」的 blob
```

### 为什么这个顺序能解决「离线复活」

如果只打墓碑而不改顺序，一台离线三天的节点可能在已知「对方已抹除」之前，
先把旧 blob 推回去，导致泄漏内容复活。

但**只要同步顺序是「先定终局、再按终局取内容」**：

- 应用了 `REMOVE X` 之后，X 已经不在本地的最终 tree 里
- 于是本地**根本不会去请求 X 的 blob**
- 机器上也不会有

**这不是靠额外机制防住的，是靠顺序消掉的。**

### 唯一要加的硬约束

新节点入网、或离线节点重连时，**必须先拉 tree，再允许推自己的东西**。
否则它可能在知道对方的抹除之前，先把旧 blob 推过去。

### 水位（watermark）

每条命令带 `(nodeID, seq)`，节点维护两个游标：

- `out_seq`：我已经推给对方、且对方**验证后回执**的最大序号
- `in_seq`：我已经拉取并应用、且本地验证通过的最大序号

## 五、删除与替换：blob 级

### 为什么是 blob 级

泄漏的内容在 blob 里，不在路径里。只删路径会让 `objects/7eb0de...` 继续躺在硬盘上——
**那不是删除，是遮眼法。**

### 协议

```
ERASE   <old_blob_sha>                    抹除
REPLACE <old_blob_sha> <new_blob_sha>     替换为另一个值
```

执行链条：

```
① 定位：在全部历史 commit 中搜出所有引用它的 tree/commit
② 重写本地：替换 blob → 重建受影响 tree → 重建受影响 commit
   （每个 commit 的 SHA 都会变，因为父链变了）
③ 广播「抹除令」而不是「新历史」
   每个节点执行：
     - 从 objects/ 物理删除 old_blob（rm，不是墓碑）
     - 把自己的历史重写成同一份新历史
     - 回执 ACK
④ 确认所有节点 ACK 之后，才算完成
```

### 代价（已确认接受）

**抹除后所有节点与历史 commit 的 SHA 全部作废**，任何曾 clone 过的外部副本不再能对齐。
因此允许 **force-push**。

### 边界

**只对「自己控制的机器 + 自己的 Git 仓库」承诺彻底抹除。**

外部托管（GitHub 等）做不到「像从没存在过」：

- force-push 之后旧对象在其 GC 前仍可按 SHA 访问
- 用户无法触发其 GC
- 任何曾经的 clone 永久持有旧 blob

**这不是技术问题，是所有权问题。** 文档必须写明，不许含糊。

## 六、审计：命令流里留「不可见节点」

### 问题

如果一个系统可以「像从没存在过一样」抹掉任何记忆，它同时也能抹掉
「谁在什么时候抹掉了什么」——这与「记录必须按实际」直接冲突。

### 决策

命令流里保留一个**内容不可见、位置与时间可见**的节点：

```
S 100644 7eb0de...  config/leak.md          ← 原始
X            [内容不可见] 原因:泄漏  by:<node> ← 抹除标记，永久保留
R 100644 4f2a91...  config/leak.md          ← 替换后的新内容
```

- 「这里被人抹过东西」永远可查 → 防篡改证词
- 「被抹的是什么」不可回读 → 防泄漏

**世界树可以改写，但「改写过」这件事本身不能消失。**

## 七、写后回读与回执

### 三种故障不能混为一谈

| 故障 | `fsync` 能防 | 回读能防 |
|---|---|---|
| 掉电丢页缓存 | ✅ | ❌ |
| 短写 / 半截文件 | ❌ | ✅ |
| 磁盘坏块 | ❌ | ✅ |

**两者都要，缺一不可。**

### 现存盲信点（必须修）

`writeObject` 里：

```go
if _, err := r.FS().Stat(dst); err == nil {
    return sha, nil          // 文件存在就当写好了
}
```

崩溃留下的半截对象会被永久信任。修法是异步回读校验：

```
写完 → 放进后台校验队列（不阻塞写入）
     → 读回来 → 重算 sha1 → 与文件名比对
     → 不一致：标记坏对象 + 报警 + 重写
```

### 三层校验

| 层 | 覆盖 | 时机 |
|---|---|---|
| 写后回读 | 新写的对象 | 异步，微秒级 |
| 后台巡边 | 存量对象 | 限速，游标推进，10 分钟 100 个 |
| 跨节点回执 | 传输正确性 | 每批一次 ACK |

### 回执必须由接收方发

```
A 推 seq 42 → B 落地 → B 自己回读验证 → B 发 ACK(seq=42, verified=true) → A 才确认
```

**A 自己说「我发成功了」只证明 socket 写进去了**，对方磁盘满、进程崩、校验失败，A 一无所知。

### `status` 要能看到

```
sync:
  BlackEggAI/zero -> hub-3060
    out  seq 1204 / 1204 已确认（对端回读校验通过）
    in   seq 1180 / 1204 已应用（24 条校验中）
    lag  24

disk verify:
  对象 38095 / 38095 已校验（最近一轮 2 分钟前）
  坏对象 0
  脏层解析失败 0
```

**从「好像同步了」变成「差分多少条」。**

## 八、多索引共存

### 现状的问题

```
① 向量目录只有一个：<DataDir>/vectors/
② manifest 检查模型名：m.Model != expectedModel → ErrStale（整份作废）
③ embed.Chain 要求：a chain requires ONE model across all providers
```

后果：远端 bge-m3 挂掉切本地小模型时，

1. 不同维度不能进同一条链 → 直接拒绝
2. 即使放行，切回时缓存已被覆盖 → **重新算 29,530 条**

**每次网络波动 = 两轮全量重建。**

### 决策：按模型分目录

```
<DataDir>/vectors/
  bge-m3/              ← 远端 1024 维，永不被本地模型覆盖
    manifest.json
    vectors.bin
  bge-small-zh-int8/   ← 本地 512 维，降级时按需建
    manifest.json
    vectors.bin
```

### 关键约束（防止双份实时开销）

**平时只算「当前正在用的那一个模型」。不在每次写入时同时更新两份索引。**

降级时才切目录；若目标目录从未建过，当场重建（边缘节点数据量小，几秒级）。

### 切回时不会腐烂

`prints` 指纹表按目录独立保存。切回 `bge-m3/` 时：

- 未变化的文档 → 直接复用，0 推理
- 缺席期间新增的 → 自动补算

**大索引不但没被踩碎，还会把缺席期间的新增自动补齐。**

### 阈值必须随模型走

向量分数分布与模型强相关，**阈值不能跨模型复用**：

| 模型 | 实测阈值量级 |
|---|---|
| `bge-m3` | 相关 0.029~0.033 / 无关 0.016 → 阈值 0.025 |
| `bge-small-zh-int8` | 需重新标定 |

`gate_threshold` 必须按 provider 配置，不许写全局常量。

（同一个坑在 BM25 上已经踩过：有人拿 0.8 当阈值，而实测分数是 12.6~59.2。）

## 九、事件流：节点间 pub/sub

工作层命令流同时是**存储同步流**与**节点间事件流**。

```
分身 A 写入
   ↓ 本地工作层产生 seq=42
   ├── pub/sub 推 seq=42 ──► 分身 B
   │                            ├── 拉 tree（seq 42 的内容）
   │                            ├── 拉缺失 blob
   │                            ├── 本地索引热插拔
   │                            └── 触发本地 remind → MCP resources/updated
```

### 两个通道，各归其位

| 通道 | 用途 | 机制 |
|---|---|---|
| memcp ⇄ memcp | 节点互联复制 | 工作层命令流 |
| memcp ⇄ 本机 Agent | 变更通知 | **MCP 原生** `resources/subscribe` |

`resource_events.go` 里的 `resourceHub` / `publish` / `publishTreeChange` 已经存在，
只需把触发源从「commit 发生」改为「工作层命令追加」。

### `remind` 的语义变化

现在是轮询式（记录基线，`status` / `since` 才告诉你动没动）。
工作层扩散后变成推送式：**树一动就知道，动的是哪些路径也知道。**

### 不是回执机制

pub/sub 解决「扩散」，不解决「对话」。
「对方读没读过」仍然要靠一条 ack 记忆（写一条 `ack/<seq>.md`），
而不是指望 pub/sub 提供送达确认。

## 十点五、提交锚点：commit 与命令流的接缝

命令流用**位点**（seq）锚定，Git 用**提交**（commit）锚定。这两套锚此前
毫无交点，于是「先传提交、再传该提交之后的命令流」这件事做不到——
对端拿着一个提交，不知道自己该从哪一位开始要，只能让上游把整棵树重发。

### 锚点表

每次提交成功后，在命令流旁边记一条 `(commit, seq)`：

```
<data>/system/oplog/<node>/<project>/<branch>.anchors.ndjson
{"seq":15660,"commit":"79b9bc78..."}
```

**seq 取提交开始之前的那一位，不是之后。** 提交期间到达的写入若也被折进
这棵树，按锚点重放只会把它们再 set 一次（幂等）；反过来记录提交之后的位点，
那些写入就永远不在任何一批增量里——幂等无害，跳过是数据丢失。

锚点与命令流分文件存放：命令流是重放依据，锚点是索引。混写会让
「命令流损坏」和「锚点损坏」共用同一条诊断路径，而两者后果完全不同。

### 协议

`opBatch` 增加 `base_commit` 字段；`/sync/ops/pull` 的请求体接受同名可选参数。

| 对端给的 base_commit | 上游行为 |
|---|---|
| 命中锚点 | 只发该位点之后的命令，`BaseCommit` 回显 |
| 不认识 | 退化为权威整树（`opTree` + `Replace`），日志出声 |
| 未给 | 按位点水位照旧 |

退化而不报错是故意的：报错会让老客户端永远同步不了，而整树恰好是
「没有基准」时唯一正确的答案。

### 用它的场景

下游通过 Git 浅拷贝拿到了某个提交（历史不要，只要终态），随后挂上命令流
继续增量。此时它的命令流水位是 0，但树已经在了——`base_commit` 让它
只取该提交之后的几条命令，而不是把几百 MB 整树再拉一遍。

## 十一、明确不做的事

1. **不做「脏层实时双写多份索引」** —— 用改路径时重建替代，避免双倍嵌入开销。
2. **不承诺对外部托管仓库的彻底抹除** —— 只能承诺自己控制的节点。
3. **不让 Agent 直接讲工作层协议** —— Agent 侧永远只见 MCP；节点间协议是服务对服务。
4. **不把审计账本纳入可改写范围** —— 世界树可以改，账本不行。
