# 架构设计：zero-memcp

> 这不是一份功能列表，而是一份决策记录。每一条都回答同一个问题：
> **为什么不用那个更常见、更省事的做法？**

---

## 一、存储层：为什么是 Git 裸仓库

### 问题

Agent 的长期记忆需要满足三个相互冲突的要求：

1. **可追溯**：任意时刻的状态都能回溯到「哪一次写入产生的」；
2. **可审计**：能对比两个分支的差异，把可疑内容隔离；
3. **抗损坏**：进程被杀、机器断电，已确认的写入不能丢。

向量数据库满足检索，但满足不了 1 和 2 —— 它的存储是「一堆浮点数组」，没有历史、没有 diff、没有不可变性。

### 决策

用 **Git 裸仓库**作为物理存储。每篇记忆是一个 blob，每次封箱是一个 commit。

带来的性质：

| 性质 | 来源 |
|---|---|
| 内容不可变 | blob 由 SHA-1 定址，改一个字节就换一个地址 |
| 完整历史 | commit 串成有向无环图，父指针永不修改 |
| 分支隔离 | 不同分支指向不同 commit，物理上互不干扰 |
| 免费审计 | `diff` 是两个树对比，不需要额外机制 |
| 通用互操作 | 任何 Git 客户端都能 clone / fetch |

### 代价与取舍

**代价**：Git 的存储模型对「大量小文件」不友好（每个 blob 一个文件，inode 压力大）。

**取舍**：记忆体量是「万篇级」而非「亿级」。一万个 blob 约 3 万 inode，现代文件系统毫无压力。用这一点换取不可变性，值得。

**不做的**：不做 `git gc` 强依赖。`gc` 是可选的优化（把松散对象打包），不跑它服务照常工作。跑过之后有 packfile，所以**必须**实现 pack 读取器 —— 否则 gc 之后记忆会「凭空消失」且无任何报错。

## 二、写入路径：为什么必须有 WAL

### 问题

一条记忆的写入涉及三个状态变更：

1. blob 落盘；
2. Git 树结构更新（要等 commit）；
3. 内存索引更新（BM25 倒排表）。

如果在步骤 2 和 3 之间进程被杀，重启后会看到「blob 在磁盘上，但索引里没有」—— 记忆存在但搜不到。

### 决策

**Write-Ahead Log**：写 blob → 追加 WAL 并 fsync → 才更新内存。

重启时重放 WAL，把「磁盘上有、索引里没有」的写入补回来。

### 三条硬规矩

**① WAL 只追加，永不重写**

重写 = 写新文件 + rename。中间被杀，最坏情况是丢掉整个原日志。只追加则任何时候被杀，最多丢最后一行。

**② 每行带 CRC32**

断电时可能写出半行。没有校验的话，重放时会把半行当成合法记录解析，产生垃圾数据。

**③ 重放遇坏行即停，并截断文件尾**

这一条最反直觉。如果不截断，下次追加会**接在半行后面**，形成一条永久损坏的记录，并毒化之后所有写入。截断的代价是丢掉那一条，不截断的代价是丢掉之后全部。

### 进度记录

`zero-memcp.checkpoint` 存字节偏移。只有当日志里**所有**条目都属于已提交的分支时才推进 —— 否则会跳过未提交的写入。

## 三、封箱时机：为什么引擎不自动提交

### 问题

常见做法是「攒够 N 条或过了 T 秒就自动 commit」。这在单人场景很省事，但在多 Agent 场景是灾难：

审计 Agent 正在 `diff audited -> raw`，后台刚好把 `raw` 推进了一个 commit，结果**未审和已审的内容静默错位**，没有任何报错。

### 决策

**引擎永不自动提交。** 封箱是语义判断，属于调用方（Agent 或人），不属于存储引擎。

`maintain()` 只做两件事：探测外部 HEAD 变动、定期 `gc`。

**代价**：调用方必须记得 `commit`。不提交的数据不会丢（WAL 保证），但不会进历史。

**收益**：任何时刻的分支状态都是某个明确的决策点，不是时钟的副产品。

## 四、分支模型：为什么 pending 要按分支隔离

### 问题

早期实现里，待提交区是 `map[path]data`。`daily@chat` 和 `daily@zero` 写同名文件时，后写覆盖先写，**且不报错**。

### 决策

`pending map[string]map[string][]byte` —— `ref → path → data`。

墓碑删除同理：`pdeleted` 也按 ref 隔离。删除与写入共享同一个 commit 边界 —— 删一条不该变成独立的即时提交，否则交错时先攒的写入会被后到的删除提交覆盖。

---

## 五、权限模型：为什么权限归项目，不归文件

### 问题

文件系统用 mode 位表达权限（`rwxr-xr-x`）。但记忆库里，一个 `.md` 文件和一个 `.sh` 脚本的意义完全不同，而它们的 mode 位可能一样。

更根本的问题：**权限是「谁能对哪个项目做什么」**，不是「这个文件的位是什么」。

### 决策

权限在 **TOML 项目级**声明：

```toml
[[project]]
name  = "blackegg/me"
owner = "zero"
mode  = "rwx------"

[[access]]
user    = "chat"
project = "blackegg/daily"
perm    = "r"
```

**Token 只带身份 + 收窄能力**：`cap` / `mount` / `roles` 只能收窄，与 TOML 取交集，永远不能放大。

### 规则注入的判定

早期用 Git 的 `100755` 位判断「这是不是规则文件」，结果把 `.githooks/pre-push`（shell 脚本）和 `export-transcripts.py`（11KB Python）当成了身份注入进去 —— 真身份（`skills/01-me/*.md`，全 100644）一个没进。

**修正**：规则判定权交给文件自己。`SKILL.md` frontmatter 里写 `inject: every_turn` 才是规则；没写就回退 mode 位；非 Markdown 一律不是规则。

## 六、挂载表：为什么表外必须完全不可见

### 决策

Token 的挂载表是 **chroot**：表外项目完全不可见。`ToVirtual` 找不到映射返回空串，**绝不回落真实地址**。

### 为什么这么严

回落的后果是：一个本该只看 `daily` 的 Agent，因为某个路径没匹配上，看到了 `me`。而这种错误**不会报错**，只会让 Agent 多知道一些不该知道的事。

「匹配不到就拒绝」是唯一安全的默认。

**受控放宽**：裸相对路径如果**唯一命中**一个项目，自动补全项目前缀；多个命中则报歧义。唯一才补，绝不猜。

## 七、索引：为什么 BM25 索引不落盘

### 决策

两类「索引」严格区分：

| 类型 | 例子 | 持久化 |
|---|---|---|
| Git 树状态 | blob、tree、commit | **必须**（真相） |
| BM25 倒排表 | 词项 → 文档列表 | **绝不**（派生物） |

倒排表是纯派生物：从 blob 全量重建只需几百毫秒（890 篇文档实测 37ms）。落盘反而引入一致性负担 —— 索引和内容不同步时，你信哪个？

启动时全量重建，永远一致。

## 八、协议层：为什么只暴露一个工具

### 问题

MCP 的常规做法是一个动词一个工具（`read_memory`、`write_memory`、`search_memory`…）。

### 决策

**单工具 `term({cmd})`**，实现 termcp 协议。

理由：**声明面等于能力面**。工具列表里看得见 `term`，就只能调 `term`。能力增长发生在命令空间（新增动词），不在 `tools/list`（新增工具）。

这带来的实际好处：上下文占用恒定。不管记忆服务有多少能力，模型只看见一个工具的 schema。

---

## 九、端口策略：为什么权限落在 socket 上

### 问题

常见做法是「服务启动时判断自己是主节点还是从节点」，用一个 `if` 拦写操作。

### 决策

**权限在 `[[listen]]` 块上声明**：

```toml
[[listen]]
addr  = "10.10.0.0:1731"
allow = ["read", "ls", "recall"]
require = "bearer"
mount = ["blackegg/daily=/daily:r@chat"]
```

三个维度：

1. **动词白名单** `allow`：没配的动词在这个端口上直接拒绝；
2. **强制凭证** `require = "bearer"`：即使来自回环地址也要求 Token；
3. **端口级挂载** `mount`：与 Token 挂载取交集，只能进一步收窄。

### 为什么不是「角色」

曾经实现过 `role = "center" | "edge"`，**这是错的抽象**，已完全移除。

Git 里没有中心/边缘 —— 每个仓库对等，能 push 还是只能 fetch 取决于**远端配置和访问控制**，不是仓库的固有属性。

同理，一个实例能写还是只能读，取决于**哪个端口、什么凭证**，不是实例的身份。全局角色开关会误伤：设成 `edge` 之后连本机 root 都写不了。

## 十、未来方向

- **`kill` / `archive` / `reset` 的 Agent 生命周期**：`refs/agents/<branch>` 登记（pid / endpoint / token jti / parent / status），`kill` 先吊销 JTI 再杀进程；
- **审计闭环**：脏流分支 → 只读审计 Agent → `diff` 提取未审 → `batch` 原子决议（提纯入主干、载荷隔离到 `private/quarantine`、推进水位 tag）；
- **center / edge 拓扑**：中心节点存密钥推上游，边缘节点只实现 `upload-pack`（只读 HTTP Git 已就绪）；
- **termcp 通道**：工具结果自动落脏流，实现「执行即记录」。
