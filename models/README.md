# 语义检索模型资产

这些文件不入库（606MB），用 `./fetch.sh` 按需下载。

## 为什么是 LaBSE 而不是 bge-small-zh

一开始用的是 `bge-small-zh-v1.5-int8`（24MB，中文单语）。实测它跨语言
能力不足，直接导致 1729 案检索失败：

| 测试 | bge-small-zh | LaBSE |
|---|---|---|
| 中文问 vs 英文思考（不同语言，同一内容） | **0.41** | **0.97** |
| 中文问 vs 中文翻译（同语言） | 0.50 | 0.84 |
| 目标切片在全库 3,294 篇中的排名 | 第 22 名 | 第 21 名 |

`bge-small-zh` 是中文单语模型，跨语言只是附带效果。同内容仅因语言不同
就掉 0.09 分，而库里排前面的中文讨论能到 0.5~0.6，目标被压到 22 名。

LaBSE 是 Google 专为跨语言句向量训练的模型，支持 109 种语言。

## 为什么最后靠 RRF 而不是向量排名

换 LaBSE 后目标排名只从 22 升到 21——**说明单靠向量治不了这个病**。
诊断后发现真正原因不是模型能力：

1. **LaBSE 分数区间压缩**：无关内容 0.79，正解 0.83，差距仅 0.04。
   绝对阈值（原来的 0.35）对 LaBSE 完全失效，全部结果都能通过。
2. **mean-pooling 稀释**：一篇 4KB 的 thinking 里只有约 100 字节提到 1729，
   平均后信号只剩 2.5%。分段 max-pooling 也救不回来（噪声块能到 0.86）。
3. **"事实"打不过"关于事实的讨论"**：库里天然有 20 段在讨论 1729，
   它们主题上确实比"只提一句 1729 的原始推理"更接近查询。

真正的解法是 **RRF 排名融合**：BM25 在精确符号（`1729`）上判别力极强
（对答案文档给 9.31 分，而向量只有 0.84~0.85 的压缩噪声），让两路按
排名贡献、双路命中自动叠加，答案文档就稳定排第一。

结论：**向量检索在这里的角色是跨语言兜底，不是主力排序。** 主力是
BM25 命中 + RRF 融合；向量负责"字面完全不同但意思相通"的那部分。

## 模型规格

- **输入**：`input_ids`、`attention_mask`、`token_type_ids`，形状 `[-1, -1]`
- **输出**：`last_hidden_state`，形状 `[-1, -1, 768]`
- **池化**：mask 加权 mean pooling，然后 L2 归一化
- **分词**：BERT WordPiece（与 bge 系列同构，分词器代码可直接复用）
- **窗口**：512 token

维度不写死在代码里——`embed.Open` 从 ONNX 元数据实测输出维度，
`vecindex` 的维度由 `New(dim)` 传入，manifest 记录并校验。
换模型时旧缓存会因名字或维度不符自动判过期重建。
